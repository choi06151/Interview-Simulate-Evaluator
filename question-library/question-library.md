# 게임 엔진 클라이언트 면접 공통 질문 라이브러리

이 목록은 개인별 추천을 만드는 재료입니다. 모든 질문을 매 회차에 그대로 사용하지 않습니다. 참가자의 실제 평가 기록에 맞는 질문을 골라 변형하고, 이미 반복한 질문은 원리·조건·상황을 바꿔 전이 능력을 확인합니다.

각 문항은 실제 평가에 사용하기 전에 포지션 레벨과 프로젝트 맥락에 맞게 조정할 수 있습니다. 질문 하나에서 확인하지 않은 역량을 추정하지 않습니다.

## C++ 및 런타임

### Q-CPP-01 — 객체 수명과 소유권

게임 오브젝트가 여러 시스템에서 참조되고 한 시스템에서 제거될 때, 댕글링 참조나 중복 해제를 막기 위해 어떤 소유권 규칙과 수명 관리를 선택하겠습니까? 선택한 방식의 비용이나 제약도 설명해 주세요.

- 후속 질문: 지연 삭제가 필요한 상황이라면 프레임 업데이트와 충돌하지 않게 어떻게 처리하겠습니까?
- 확인 신호: 소유자와 관찰자 구분, 수명 경계, 파괴 시점, 대안과 트레이드오프.

### Q-CPP-02 — 컨테이너와 성능

매 프레임 수천 개의 엔티티를 순회하는 시스템에서 자료구조를 선택할 때 어떤 접근 패턴과 메모리 배치를 고려하겠습니까? 병목 여부는 어떻게 확인하겠습니까?

- 후속 질문: 엔티티 생성/삭제가 매우 잦다면 선택이 어떻게 달라질 수 있습니까?
- 확인 신호: 접근 패턴과 캐시 지역성, 할당/삭제 비용, 실제 측정과 대안 비교.

## 엔진 및 게임플레이 구조

### Q-ENG-01 — 프레임 업데이트 순서

입력 처리, 캐릭터 이동, 애니메이션, 물리 업데이트 순서가 결과에 영향을 주는 사례를 설명하고, 시스템 간 순서를 어떻게 관리하겠습니까?

- 후속 질문: 프레임률이 달라질 때 동작 결과를 일정하게 유지하려면 무엇을 바꾸겠습니까?
- 확인 신호: 의존 관계, 고정/가변 시간 간격의 역할, 순서 결정과 검증 방법.

### Q-ENG-02 — 게임플레이 상태 설계

캐릭터가 공격 중 피격되어 경직 상태에 들어가는 기능을 설계해 보세요. 어떤 상태와 전이를 두고, 입력·애니메이션·취소 규칙을 어떻게 맞추겠습니까?

- 후속 질문: 상태 조합이 늘어나 복잡해질 때 구조를 어떻게 정리하겠습니까?
- 확인 신호: 상태 전이와 우선순위, 취소/종료 조건, 데이터 책임과 테스트 가능한 경계.

### Q-ENG-03 — 비동기 리소스 로딩

게임 플레이 중 대형 리소스를 비동기로 로드할 때 로딩 중 상태, 취소, 실패, 객체가 먼저 파괴되는 경우를 어떻게 처리하겠습니까?

- 후속 질문: 로딩 완료 콜백이 다른 스레드에서 온다면 어떤 제약을 확인해야 합니까?
- 확인 신호: 수명과 취소 토큰/요청 ID, 스레드 안전성, 실패 경로, 사용자 경험과 성능.

## 성능과 디버깅

### Q-PERF-01 — 프레임 타임 급증

특정 전투 장면에서 프레임 타임이 급격히 늘어납니다. 원인을 좁히고 수정 효과를 확인하는 과정을 순서대로 설명해 주세요.

- 후속 질문: CPU와 GPU 중 어디가 병목인지 어떤 자료로 구분하겠습니까?
- 확인 신호: 재현 조건, 기준선, 프로파일링, 병목 가설, 전후 측정과 회귀 확인.

### Q-PERF-02 — 메모리 증가/누수 의심

플레이 시간이 길수록 메모리 사용량이 증가합니다. 재현·분류·원인 확인·수정 검증을 어떻게 진행하겠습니까?

- 후속 질문: 캐시가 의도된 증가인지 누수인지 어떻게 판별하겠습니까?
- 확인 신호: 스냅샷 비교, 소유자/참조 추적, 재현 가능한 시나리오, 정상 상한 확인.

### Q-DEBUG-01 — 재현 어려운 버그

특정 기기에서 간헐적으로만 발생하는 입력 지연 버그를 전달받았습니다. 어떤 정보를 먼저 모으고, 어떻게 원인을 분리하겠습니까?

- 후속 질문: 로그를 추가해도 현상이 사라지거나 재현 빈도가 달라지면 어떻게 하겠습니까?
- 확인 신호: 환경/빌드/입력 기록, 관측 수단, 경쟁 가설, 최소 재현, 수정 후 검증.

## 시스템 및 플랫폼

### Q-SYS-01 — 네트워크 상태 변화

네트워크 지연이나 일시 단절이 있는 게임에서 클라이언트가 책임질 부분과 서버에 맡길 부분을 어떻게 나누겠습니까?

- 후속 질문: 화면 반응성과 서버 판정이 어긋날 때 사용자 경험과 정합성을 어떻게 조정하겠습니까?
- 확인 신호: 권한 경계, 예측/보정의 개념, 실패 상태 처리, 트레이드오프.

### Q-SYS-02 — 플랫폼별 차이

한 플랫폼에서는 정상인 기능이 다른 플랫폼에서 입력 또는 파일 처리 문제를 일으킵니다. 공통 코드와 플랫폼별 코드를 어떻게 구분하고 검증하겠습니까?

- 후속 질문: 조건부 컴파일이 늘어나 유지보수가 어려워지면 어떤 대안을 검토하겠습니까?
- 확인 신호: 추상화 경계, 플랫폼 API 제약, 빌드/테스트 매트릭스와 회귀 확인.

## 협업 및 업무 상황

### Q-COL-01 — 기술적 의견 충돌

개발 중 동료와 시스템 설계 방향이 충돌했습니다. 상대가 다른 선택을 하는 이유를 모르는 상황이라면 무엇부터 하고, 어떻게 결론을 내리겠습니까?

- 후속 질문: 일정 때문에 오늘 안에 결론이 필요한데 합의가 되지 않으면 어떻게 하겠습니까?
- 확인 신호: 전제 확인과 경청, 사용자/기술 근거 비교, 결정 기준과 책임자, 결정 후 실행 및 재검토.

### Q-COL-02 — 기획 변경과 일정 압박

출시 직전에 요구사항이 바뀌어 현재 일정으로는 모든 기능을 마무리하기 어렵습니다. 무엇을 확인하고 어떤 선택지를 제안하겠습니까?

- 후속 질문: 품질 위험을 감수하자는 압박이 있을 때 어떻게 설명하고 기록하겠습니까?
- 확인 신호: 범위·리스크·의존성 파악, 우선순위 대안, 영향과 근거의 투명한 공유.

### Q-COL-03 — 실수와 회고

본인의 변경으로 빌드나 기능에 문제가 생긴 것을 발견했습니다. 발견 직후부터 재발 방지까지 어떻게 대응하겠습니까?

- 후속 질문: 문제가 다른 팀의 작업에도 영향을 주었다면 누구에게 무엇을 알리겠습니까?
- 확인 신호: 영향 범위와 복구 우선, 적시 공유, 원인 분석, 비난보다 재발 방지 행동.

### Q-COL-04 — 피드백 수용

코드 리뷰에서 본인이 중요하게 생각한 구현 방식에 큰 수정 의견을 받았습니다. 동의 여부를 어떻게 판단하고, 이후 어떻게 대응하겠습니까?

- 후속 질문: 리뷰어와 근거가 다르면 어떻게 해결하겠습니까?
- 확인 신호: 피드백의 목적 이해, 근거 검토, 반론의 구체성, 합의 또는 결정 후 반영.

### Q-COL-05 — 모호한 요구사항

캐릭터 조작감이 “더 부드럽게” 느껴지도록 바꿔 달라는 요청을 받았지만 성공 기준이 없습니다. 구현 전에 무엇을 질문하고 어떻게 검증하겠습니까?

- 후속 질문: 정량 지표와 플레이테스트 의견이 서로 다르면 어떤 판단 절차를 두겠습니까?
- 확인 신호: 모호한 표현을 관찰 가능한 목표로 변환, 이해관계자 확인, 반복 측정과 질적 검증의 조합.
