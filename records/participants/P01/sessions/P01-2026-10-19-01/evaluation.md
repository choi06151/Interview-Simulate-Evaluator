## 잘한 점

- Q4에서 Unreal GC 관련 지식의 한계를 숨기지 않고 모른다고 밝혔습니다. 이는 정답 근거로 계산되지는 않지만, 지식의 공백을 명확히 드러낸 답변입니다.
- Unreal과 Unity를 사용한 순서, Blueprint·셰이더·OpenGL·C# 경험을 설명해 학습 경로를 제시했습니다. 다만 사용 경험의 깊이는 추가 질문으로 검증해야 합니다.
- 만들고 싶은 기능을 이후에도 확장·개량하기 쉬운 구조로 만들고 싶다는 개발 목표를 밝혔습니다. 실제 설계 역량은 확인되지 않았지만 다음 면접에서 구체 사례로 검증할 가치가 있습니다.

## 우선 보완점

1. **Unreal의 객체 수명과 GC:** Q4에서 엔진 GC와 C++ 객체 관리의 차이를 설명하지 못했습니다. `UObject` 수명, GC가 추적하는 참조, `UPROPERTY`/엔진 컨테이너 참조와 raw pointer 차이를 설명하고 간단한 객체 참조 사례로 확인하는 연습이 필요합니다.
2. **그래픽스 이해를 구체화:** Q2의 “렌더링과 셰이더가 어떻게 돌아가는지 안다”는 주장을 파이프라인 흐름, 셰이더 단계, 입력/출력 데이터와 연결해 설명하는 연습이 필요합니다.
3. **엔진 경험을 비교 근거로 제시:** Q3에서 사용량 외에 Unreal과 Unity에서 직접 구현한 기능, 각 엔진에서 선택이 달랐던 이유와 트레이드오프를 사례로 준비해야 합니다.
4. **답변을 근거 중심으로 구조화:** 각 답을 `핵심 주장 → 작동 원리/경험 사례 → 선택 이유 또는 한계` 순서로 짧게 정리하고, 실제로 설명할 수 있는 깊이와 경험 범위를 명확히 구분하는 것이 좋습니다.

## 기술적으로 정확히 짚을 부분

면접관의 질문은 “C++에는 가비지 컬렉터가 없고 Unreal에는 있다”는 대비를 전제로 했습니다. 더 정확히는 표준 C++ 언어 자체가 자동 가비지 컬렉션을 제공하지 않지만, Unreal은 `UObject` 계층에 엔진의 추적형 GC를 제공합니다. GC가 추적하는 참조 그래프에 포함된 객체는 살아 있는 것으로 유지되고, 추적되지 않는 raw pointer만으로는 객체 생존이 보장되지 않습니다. 일반 C++ 객체는 별도의 C++ 수명 관리 규칙을 따릅니다. 최재원 님은 이 차이를 모른다고 답했으므로 해당 질문에서 기술 이해의 증거는 확인되지 않았습니다. [Epic의 Unreal Object Handling 문서](https://dev.epicgames.com/documentation/unreal-engine/unreal-object-handling-in-unreal-engine)

## 총평

현재 답변에서는 여러 도구와 엔진을 접한 이력, 확장하기 쉬운 개발을 지향하는 동기는 확인됩니다. 그러나 그래픽스와 엔진 구조에 대한 설명이 주장 수준에 머물렀고, Unreal GC 질문에서는 핵심 개념을 모른다고 답했습니다. 기능 구현, 성능, 디버깅, 협업 대응은 질문되지 않아 판단할 수 없습니다. 다음 회차에서는 GC와 엔진 구조를 먼저 확인하고, 그래픽스 경험을 구체적인 구현 사례로 검증해야 합니다. 이번 점수만으로 전체 실무 역량을 결론 내릴 수는 없습니다.

## 다음 연습 계획

1. **Unreal 객체 수명/GC:** `UObject` 참조가 어떻게 유지되는지 그림으로 정리하고, `UPROPERTY` 참조와 raw pointer의 차이를 예제로 설명합니다. 완료 기준은 GC가 객체를 회수하는 조건과 참조를 유지하는 방법을 정확히 설명하는 것입니다.
2. **렌더링 파이프라인:** OpenGL 또는 익숙한 엔진 기준으로 vertex data부터 셰이더 단계와 화면 출력까지 한 프레임 흐름을 설명합니다. 완료 기준은 각 단계의 입력·출력과 자신이 직접 다룬 영역을 구분하는 것입니다.
3. **엔진 비교 사례:** Unreal과 Unity에서 실제 만든 기능 하나를 골라 구성 요소, 생명주기, 데이터 흐름, 선택 이유를 비교합니다. 완료 기준은 “더 익숙하다”를 넘어 구체적인 기술 차이와 맥락을 설명하는 것입니다.
