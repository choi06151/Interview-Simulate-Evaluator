## Q3. 인벤토리 UI와 병렬 처리

**면접관:** 인벤토리 같은 경우에는 UI가 갱신이 돼야 하잖아요. 그러면 UI 갱신을 보장할 때 병렬 처리 관련해서 자원이 중복되는 상황 같은 경우에는 어떻게 해결하실 수 있나요?

**지원자:** 병렬 처리할 때 자원이 중복되는 상황 같은 경우에는 옵저버 패턴을 이용해서 인벤토리에 아이템의 개수 등에 변화가 생겼을 때 그런 것을 옵저버 패턴을 이용해서 단순히 숫자 등을 변화시킬 수 있도록 해서 성능적인 부담을 최소화할 수 있는 방향으로 코드를 구성할 것 같습니다.

## Q4. 다양한 몬스터 설계

**면접관:** 몬스터를 설계하고 구성할 때 다양한 몬스터를 여러 타입으로 구성한다면, 새로운 몬스터를 추가할 때 어떤 식으로 구조를 설계하시겠습니까?

**지원자:** 일단 몬스터 같은 경우에는 기본적으로 여러 종류의 몬스터를 만들 경우에는 상속을 이용해서 하는 것으로 생각하고 있고, 추가적인 패턴이 있다면 팩토리 패턴을 이용해서 몬스터마다 기본적으로 공유하는 특성을 반영하는 식으로 하고, 또 몬스터마다 차이가 일반 몬스터랑 엘리트 몬스터의 경우 차이가 나는 점을 추가적으로 코드로 덧붙이는 형식으로 전체적으로 프로젝트를 구성할 것 같습니다.

## Q5. 상속과 컴포지션의 차이

**면접관:** 몬스터 종류가 다양해지는 것에 대해서 말씀하셨는데, 상속이랑 컴포지션의 차이를 명확하게 설명해 주실 수 있나요?

**지원자:** 상속의 경우에는 Is-A 관계이고, 컴포지션 같은 경우에는 Has-A 관계입니다.

좀 더 풀어서 설명하자면 상속 같은 경우에는 부모 클래스와 자식 클래스로 이루어져 있고, 부모 클래스의 어떤 특성들을 자식 클래스가 상속받는다, 이런 개념으로 저는 생각하고 있고요.

컴포지션 같은 경우에는 예를 들어서 자동차 같은 경우에는 여러 부품들로 구성되어 있는데, 여러 컴포지션으로 구성되어 있는 자동차를 만드는 그러한 관계라고 저는 생각하고 있습니다.

## Q6. Unity에서 컴포지션을 선호하는 이유

**면접관:** 유니티에서는 컴포지션을 좀 더 선호하는데 그 이유를 설명해 주실 수 있나요?

**지원자:** 제가 생각하기에는 컴포지션을 더 선호하는 이유가 아무래도 유니티에서 자체적으로 만들어 놓은 어떤 기능들을 컴포지션의 형태로 미리 만들어져 있고, 상속 같은 경우에는 아무래도 사용자가 직접 구성해서 만들어야 되는 경우가 많다 보니 아무래도 유니티에서는 컴포지션 구성을 더 선호하는 것 같습니다.

## Q7. ScriptableObject를 활용한 런타임 데이터 변경

**면접관:** 기획자가 코드 수정 없이 유니티의 수치 데이터를 변경하도록 ScriptableObject를 이용해서 만들잖아요. 그때 어떻게 이거를 활용하고 런타임 데이터 변경 시 주의사항에 대해서 말씀해 주실 수 있나요?

**지원자:** 다시 한번 말씀해 주시겠습니까?

**면접관:** 기획자가 코드 수정 없이 ScriptableObject를 활용해서 데이터를 변경할 수 있도록 하는데, 그걸 어떻게 활용하고 런타임 데이터 변경할 때 주의사항에 대해서 말씀해 주실 수 있나요?

**지원자:** 기획자가 ScriptableObject를 이용해서 데이터를 변경하는 형식은 아무래도 실제 런타임 과정에서 실제로 적용되는 수치를 변경하는 경우일 텐데, 다만 런타임에서 일어나는 데이터 변경 같은 경우에는 최대한 성능상 영향이 덜 가는 쪽으로 변경하는 걸로 알고 있습니다.

## Q8. ScriptableObject 사용 경험

**면접관:** 프로젝트를 하시면서 데이터를 저장하고 관리하는 방식이 여러 개잖아요. 그중에서 ScriptableObject를 사용하셨던 이유를 경험담으로 한번 풀어주실 수 있나요?

**지원자:** 제가 알기로는 데이터를 관리하는 방식이 CSV를 이용해서 하는 방식도 있고, ScriptableObject를 이용하는 방식도 있는데요.

제가 ScriptableObject를 이용했던 경우는 CSV에 비해서 기본적으로 관리해야 될 데이터가 좀 적은 경우에 아무래도 직접적으로 데이터를 바로 고칠 수 있다 보니 좀 더 소규모로 관리되는 데이터 형식에 대해서 ScriptableObject 방식을 적용했던 것으로 알고 있습니다.
